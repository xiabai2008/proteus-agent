## 一、结构性缺口（最高优先级）

### R-1 DSH 主线下「不传 mode」= 无任何模式保护（**已修** `eccd212`）

> 状态（2026-09-22 复核）：**已修**——MCP server 在构造期解析服务端 `default_mode`，
> 省略 `mode` 时回落到该模式而非 `None`。下面的现象描述保留为**修复前**的实测记录，
> 不是当前行为（原文不动，状态以本行为准）。

**位置**：`penagent/mcp.py` 的 `_agent(mode_id="")` → `mode=None` 分支

**现象**（本轮实测，2026-09-21）：

```
=== 无模式(DSH 模型没传 mode) ===
  mode      = None
  sandbox   = None          <- 沙箱策略完全缺失
  max_steps = 12            <- 而非模式的 40/60
  memory.ns = default       <- 而非模式分区（记忆/技能落错分区）
  工具数    = 20
  sqlmap_auto: dangerous=True -> 无沙箱裁决，直跑宿主
  nuclei_scan: dangerous=True -> 无沙箱裁决，直跑宿主
  fscan_scan : dangerous=True -> 无沙箱裁决，直跑宿主
```

**为什么严重**：DSH 会话里模型调 `mcp__proteus__pentest_run` 时，`mode` 是**可选参数**
（`mcp.py` 的 `SERVER_TOOLS` 描述里写了建议值，但属提示词级约束）。模型一旦不传：

1. **沙箱裁决完全消失**——危险 CLI 工具（sqlmap / nuclei / fscan）**直跑宿主**
2. 记忆/技能落到 `default` 分区，模式间隔离失效
3. 步数预算退回 12，判定器退回默认 `evidence_chain`（CTF 任务永远拿不到 flag 判定）
4. 违反 AGENTS.md 硬规则 1（"模式约束必须机制性生效，禁止靠模型自觉"）——这里是靠模型自觉传参

**实测到的荒谬对称性**（同一台机器，Docker 守护进程不可用）：

| 路径 | sqlmap/nuclei/fscan 结果 |
|---|---|
| 不传 mode | **直跑宿主**（无隔离） |
| 传 pentest-standard（sandbox=docker） | **被拒绝**（容器不可用） |

即：**为了让工具能用，用户/模型会倾向于不传 mode，从而失去全部模式保护**。

**建议修法**（待定，需设计）：给 `PentestMCPServer` 加默认模式（启动参数或从 DSH preset 传入），
未显式指定时回落到默认模式，而非 `None`；并把 mode 选择从"模型可选参数"提升为
"服务端配置"（与 `--targets` / `--authorize` 同级）。

### R-11 Docker 守护进程闪断导致隔离工具不可用（F-E2E-4，观察）

- **证据**（本轮实测）：传 `pentest-standard` 时 `sqlmap_auto`/`nuclei_scan`/`fscan_scan` 全部 `allowed=False`，原因 `sandbox=docker 但容器不可用（docker 守护进程不可用: failed to connect to the docker API）`
- **影响**：**本机当前无法执行任何高危 CLI 工具**（只要它们的模式是 sandbox=docker）
- **这是 R-1 的直接诱因**：用户为绕开此限制会不传 mode，反而失去全部保护
- **建议**：属基础设施问题，但内核侧应给出**可操作的提示**（当前只是 `allowed=False` + 一句原因）；或支持"降级为 local 但要求显式确认"的档位

**2026-09-21 复核（Docker 恢复后）**：基础设施已恢复——`docker version` → **29.5.2**，
`docker run --rm hello-world` → 退出码 0；`sandbox=docker` 档对危险工具由
`allowed=False` 变为 **`allowed=True, isolated=True`**（sqlmap/nuclei/fscan 实测）。

**但复核揪出一个此前被掩盖的真实缺陷**：`DockerRunner.wrap()` 把宿主路径
**同时用作** `-v` 的容器侧与 `-w`，而容器只认 Linux 路径。实测：

| 写法 | 结果 |
|---|---|
| `-v <宿主>:/work -w /work` | returncode **0**，输出 `container-ok` ✓ |
| `-v <宿主>:<宿主> -w <宿主>`（原写法） | returncode **125**，`the working directory 'D:\...' is invalid` ✗ |

Linux 上 `os.getcwd()` 本就是合法容器路径，缺陷不显形；**Windows 上隔离执行全线失败**。
此前被掩盖是因为 Docker 不可用时 `decide()` 直接拒绝、根本走不到 `wrap()`。

**已修**：宿主路径只用于 `-v` 宿主侧，容器侧固定映射 `CONTAINER_WORKDIR = "/work"`，
`-w` 也用容器内路径。回归用例
`tests/test_sandbox.py::test_docker_container_execution_actually_works`（**真跑容器**，
修复前必然失败）。

### R-15 容器内跑不了外置工具（专用镜像缺口）（**已闭环** 2026-09-23）

- **发现时间**：2026-09-21（R-11 复核时）
- **现象**：路径缺陷修复后，容器内**能跑 python**，但跑不了宿主的外置工具
  （sqlmap / nuclei / fscan / RsaCtfTool 等）：
  - 默认镜像 `python:3.12-slim` 内没有这些二进制；
  - `ctf_tools.json` 的 `{python}` 展开为**宿主**解释器路径
    （如 `<PY312>\python.exe`），容器内不存在。
- **证据**：实测 `-v <宿主>:/work -w /work python:3.12-slim python -c ...`

- **影响**：`sandbox=docker` 模式下外部 CLI 工具的隔离执行**实际不可用**——
  只有内置 function 工具与镜像自带的 python 能真跑。
- **建议**：建专用镜像（预装所需工具）或用 requirements 注入；
  `PENTEST_DOCKER_IMAGE` 环境变量已预留镜像切换（`penagent/sandbox.py`）。
  `docs/沙箱降级评估.md` 已把此项列为"待 Docker 稳定后补测"，本次复核确认
  缺口真实存在。

### R-16 `pentest-standard` 的 network_egress=false 与渗透工具出网需求矛盾（**已决策并实施 2026-09-21**）

- **发现时间**：2026-09-21（R-15 第二轮）
- **现象**：本轮给 `external_tools.json` 的 16 个工具如实声明了 `network: true`
  （目标都是远程主机，必须出网）。但 `pentest-standard` 的
  `scope.network_egress: false` 会**拒绝所有声明出网的工具**——即该模式下
  16 个渗透工具全部不可用。
- **证据**：`penagent/agent.py` 的 `Policy.check` —
  `if not self.mode.scope.network_egress and getattr(spec, "network", False):`
  → 拒绝并给出"模式关闭网络出口"；`penagent/sandbox.py` 的
  `SandboxPolicy.decide` 有同款裁决（两层冗余）。
- **为什么此前没暴露**：`external_tools.json` 的工具**从未声明过 `network`**
  （上一轮才补的字段解析），这条闸门从未触发——**补了声明才让它显形**。
- **决策（2026-09-21，用户拍板选①）**：`pentest-standard` 改
  `network_egress: true`——承认渗透测试本质必须触达目标，"禁止出网"的
  渗透模式语义自相矛盾；目标边界由已有的 `target_allowlist` 硬校验独立
  承担（硬规则 3，任何模式下越界目标一律拒绝），出网开关不重复设闸。
- **实施**：`modes/pentest-standard.yaml` 的 scope 行改为
  `{target_allowlist: required, network_egress: true}` 并附决策注释；
  `modes/base.yaml` 保持 `false` 不变（安全缺省，由各模式显式覆盖）；
  `Policy.check` / `SandboxPolicy.decide` 两层裁决**代码未动**——机制
  （egress=false 拒绝出网工具）保留，供其他模式按需使用。
- **遗留注意**：出网后目标可达面变宽，但 `target_allowlist` 仍是硬边界
  （`Policy.authorize` 白名单校验先于一切工具执行），安全姿态不受削弱。

### R-18 naabu 内置解析器读不到容器特殊名 `host.docker.internal`（已缓解 2026-09-21）

- **发现时间**：2026-09-21（R-15 第三轮）
- **现象**：`naabu -host host.docker.internal ...` 报
  `FTL Could not run enumeration: no valid ipv4 or ipv6 targets were found`；
  加 `-v` 后可见 `WRN no IP addresses found for host: host.docker.internal`。
- **根因**：容器内 `/etc/hosts` **并无** `host.docker.internal` 条目
  （实测只有 localhost 与本机名），该名字由 Docker DNS
  （`/etc/resolv.conf` → `192.168.65.7`）解析；naabu 用自带解析器，
  **不读 `/etc/hosts`**。且该路径解析**不稳定**：同一命令连跑 3 次，
  实测约一半直接报错（DNS 抖动）。
- **影响面**：只影响"工具自带解析器 + Docker 特殊名"的组合。公网/内网域名
  （走正常 DNS）与 IP 目标不受影响——**生产路径的常见目标形态没问题**。
- **缓解**：
  1. `external_tools.json` 的 `naabu_scan` 追加 `-sr`（system-resolver 兜底，
     实测对 127.0.0.1/宿主名有效，且不影响常规解析）；
  2. 回归用例**先由容器解析一次、再把 IP 传给 naabu**（不在测试里赌 DNS 抖动）。
- **仍未根治**：`-sr` 兜底后对 Docker 特殊名仍可能抖动一次即失败（naabu
  不重试）。若将来生产确需宿主名目标，应在上层（工具调用前）做解析与重试，
  而不是改工具参数。

### R-22 宿主桥审计是全局的，未按 session → preset 过滤（**已修** 2026-09-22）

**位置**：`dsh/proteus-bridge/index.mjs`（host 平面 bundle 订阅 `session/event`）

**现象**：同一个 DSH 进程里**所有会话**的工具调用都会进链。实测链上混有非
Proteus 会话的 `read` / `grep` / `agent_teams_*` 调用。

**为什么是问题**：证据链是"结论可机验"的载体，也是 `--suite dsh-session` 的
判分输入。混入他会话调用后，"这条链属于哪次 Proteus 任务"失去依据——判分函数
（`score_from_evidence`）读到的是**整个进程**的动作合集。

**建议**：插件补一层 session → preset 映射，按 preset 归属过滤后再入链；或在链
记录里带上 preset 标识，由消费端（导入器 / 评分卡）过滤。

**来源**：`docs/DSH插件化与内核旁路治理.md` 第二节末的"已知边界"——该文承诺
"记进待办，不在本轮"，本条即兑现那次承诺。

**修法（2026-09-22）**：判据是 `SessionHeader.agentPreset`
（`packages/core/session/src/types.ts:93`，源码核实）。

- **插件侧**：每条审计记录带 `preset` 归属；另可配 `presets: ['proteus']`
  直接不记别的会话（缺省空 = 全记但打标）。
- **导入器侧**：`preset` 随 observation 与 tool_call 一起入链。
- **消费端**：`--suite dsh-session` 默认只算 `preset=proteus` 的记录
  （`--preset ''` 关闭过滤）。
- **关键取舍**：**归属未知（`''`）不过滤**。字段是新加的，老链没有它；形状变化
  时也可能取不到。按未知保留，比按未知丢弃安全——丢数据是静默的，多留是可查的。
- **裁决记录的归属是尽力而为**：`tools/pre-execute` 的载荷里没有 session，
  只能顺着 `exec.agent` 摸，取不到就是 `''`；权威归属来自 `session/event` 那条路。

### R-23 目标动作裁决的两条边界（观察，2026-09-22）

**位置**：`dsh/.agent-presets/proteus/proteus-tools-policy.mjs`

1. **只管 shell 工具**（`shellTools: [pwsh, bash]`）：模型改用其它能发网络请求的
   宿主工具（如 `web_fetch`）时本层不介入。实测那次由 DSH 自身 web provider 拒绝
   （`WEB_BLOCKED_URL`，provider 内建 SSRF 防护）——属另一道闸，**不是本层的覆盖**。
2. **目标识别是启发式**（URL / `--host` / `-u` / 裸 IP）：命令里做变量拼接或编码
   绕过时可能认不出。定位是"提高旁路成本 + 留痕"，**不是密不透风的 egress 管控**
   （DSH 没有 egress 官方词汇，能力边界见该设计文档第二节）。

**附带的档位语义**：`ask` 在**无审批应答者的 profile**（headless）里等价于拒绝
（fail-closed，实测 `requires approval, but …`）；web 会话里才是弹审批卡片。
默认档位在不同入口的实际效果不同，别把"默认 `ask`"当成宽松——与本清单 R-12 同类。

### R-25 外部 MCP 发现把"不可达"变成"卡满 timeout"，拖死内核启动（**已修** 2026-09-24）

**发现过程**：为"以 DSH 为主体"做启动体检时实测——Docker 守护进程未启动，
按 preset 原样拉起内核（`--discover-mcp`）后 **300s 拿不到 `tools/list`**。

**现象（实测数字）**：

| 场景 | 耗时 |
|---|---|
| 单个容器 server 探测（把 timeout 压到 12s） | **精确 12.0s**（不是"快速失败"） |
| 6 个容器 server + 1 个 HTTP server 按仓库真实配置 | 5×300 + 60 + 120 ≈ **23 分钟**才进入 serve 循环 |
| 对照：不带 `--discover-mcp` | **0.5s** |

**根因（两条，都在 `penagent/mcp_client.py`）**：

1. `_read_response` **不感知子进程退出**：`_pump` 线程在 stdout EOF 后静默结束，
   等待者仍要等满 `spec.timeout`——而 Docker 不可用时子进程 **0.2s 就退出了**。
2. `stderr=subprocess.PIPE` **接了却没人读**：子进程 stderr 写满 64KB 就会永久阻塞
   （另一类"卡满 timeout"），且 Docker 的错误信息（在 stderr 上）全部丢失。

叠加因素：`cmd_mcp` 是**先 discover、后 serve**，所以这段时间内核连 `initialize`
都读不到；DSH 侧 `failOnStartupError: false` 会把它变成"静默没有
`mcp__proteus__*`"，而 preset 的 kernelGuard（deny）随即把目标动作全拒。

**修法**：

| 改动 | 内容 |
|---|---|
| EOF 哨兵 | `_pump_stdout` 在 EOF 时放 `None` 进队列；`_read_response` 收到即失败（带退出码 + stderr 尾巴，最多等 1s 拿退出码） |
| stderr 尾巴 | 新增 `_pump_stderr`（deque maxlen=20）：既防管道写满死锁，又给失败原因 |
| 全局预算 | `discover_mcp(..., budget=)` + `DEFAULT_DISCOVER_BUDGET=180s`：剩余预算**夹住**单个 server 的 timeout，耗尽即跳过剩余 server 并记 note |
| 按名发现 | `--discover-mcp` 从 `store_true` 改为可选值：裸写 = 全部，`--discover-mcp seckb,chameleon` = 子集；`--discover-budget` 可调 |

**复测（2026-09-24，Docker 未起）**：`--discover-mcp` 全量启动 **6.7s**、
注册 **49** 个工具（chameleon 12 + seckb 4 + rayscan 适配器 1 + 内核基数 32），
6 个容器 server 全部快速失败并记入 notes。

**回归用例**（`tests/test_registry.py`，7 条）：EOF 快速失败（含耗时上界）、
退出码与 stderr 尾巴、全局预算跳过、预算夹住单 server timeout、按名子集、
写法归一、build_center 透传。

### R-26 CTF 模式的 capability.allow 写的是抽象契约名，HTTP 能力被自己锁死（**已修** 2026-09-24）

**发现过程**：为"以 DSH 为主体"做模式体检时实测（`authorize=True`）：

```
== ctf-web
   http_raw       allowed=False  rule=mode   ← 不在 capability.allow 内
   codec_decode   allowed=True
   python_solve   allowed=True   （ask 被 --authorize 抬起）
```

**根因**：`modes/ctf-web.yaml` 的 `capability.allow` 写的是**抽象契约名**
（`http_test` / `browser_auto` / `script_run` / `file_read` / `crypto_tools`），
而 allow 是**精确匹配**——真实注册名是 `http_raw` / `http_probe` / `python_solve`…
于是 CTF 模式连一个 HTTP 请求都发不出去（CTF Web 题直接做不了）。
`--authorize` 抬不动它：allow 未命中与 `hard_deny` 同类（见 R-13 的表）。

**为什么一直没暴露**：写错名字**不报错**，只在执行期静默拒绝；而 CTF 评测
（33 题）走的是 `python_solve` / `codec_*` 这条不依赖 HTTP 的链路。

**修法**：

| 改动 | 内容 |
|---|---|
| 名单改真名 | `ctf-web` / `ctf-crypto` 的 allow 全部换成真实注册名 |
| 前缀通配 | `Capability.allows` / `Permission.level_for` 改用 `fnmatch` 匹配，支持 `seckb_*` / `binwalk_*` 这类**家族通配**——容器 MCP 的工具数随镜像演进，逐条列举必然漂移 |
| 同类清理 | `pentest-standard` 的 `auto_approve` 去掉契约键（`httpx` / `subfinder` / `dnsx` / `tlsx_scan`），只留真名；`require_confirm` / `hard_deny` 明确允许写"尚未安装的前瞻名"（死条目只增加摩擦，不会静默放行） |
| 机制性把关 | `tests/test_modes.py::test_mode_tool_lists_reference_real_names`：所有模式的 `allow` / `auto_approve` 每一项都必须能解析到真实注册名，或指向已声明的 MCP server 家族——**写错名字即测试失败** |

**复测**：`ctf-web` / `ctf-crypto` 下 `http_raw` → `allowed=True`，
`nuclei_scan` → 仍被拒（`capability.deny` 语义不变）。

### R-27 MCP 工具面不按模式裁剪：CTF 工具从不可见、底层调用不过模式裁决（**已修** 2026-09-24）

**发现过程**：做 P0-3（"选中 preset 即用"）时实测三种模式下的 `tools/list`：

```
== pentest-standard: 33 工具；CTF 工具 无
== ctf-web:          33 工具；CTF 工具 无     ← 应为 14
== ctf-crypto:       33 工具；CTF 工具 无     ← 应为 11
```

**根因（三条，都在 `penagent/mcp.py`）**：

1. **CTF 工具从不出现**：`_tools_schema()` 走 `center.schemas()`（无模式），而
   `entry.modes=('ctf-web','ctf-crypto')` 的工具在 `mode_id=None` 下
   `available_in()` 为假——**CTF preset 的核心工具一个都看不到**。
2. **模式裁决对底层调用无效**：底层分支用 `self.registry.execute()`，那是
   启动时的全量注册表（不带模式、`kernel_only=True` 连 `pentest_*` 都漏），
   闸门的 `Policy` 也没带 mode——`capability.allow/deny` 只对 `pentest_run`
   那条路生效。
3. **没有 `listChanged`**：`initialize` 声明 `capabilities.tools = {}`，
   且从不发 `tools/list_changed`——模式切换后客户端不会重取工具面。

**修法**：

| 改动 | 内容 |
|---|---|
| 统一判据 | 新增 `_mode_registry(mode)`：`build_registry(mode, kernel_only=False)`（含 `entry.modes` 过滤）→ 挂**带 mode 的 PolicyGate** → `filtered_registry`（capability 过滤）；按模式 id 缓存 |
| 列表与执行同源 | `tools/list` 与底层 `tools/call` 都走它——不会出现"列表里没有却能调用"或反过来的裂缝；被裁掉的工具直接是"未知工具" |
| 动态通知 | `initialize` 声明 `tools.listChanged: true`；`pentest_set_mode` 之后、或 `/proteus-mode` 命令直接写会话文件之后，**下次请求前**补发 `notifications/tools/list_changed`（DSH 的 mcp-client 注册了 `onChanged → refreshTools()`） |
| 工具面补全 | CTF 模式 allow 加入元能力（`pentest_set_mode` / `pentest_evidence` / `pentest_missions` / `pentest_skills`）——否则 CTF 会话连"切模式"都做不到 |

**复测（真机 stdio，独立 data 目录）**：

| 模式 | 工具数 | CTF 工具 | nuclei_scan | pentest_run |
|---|---|---|---|---|
| pentest-standard | 33 | 无 | 有 | 有 |
| ctf-web | 14 | 5 件齐全 | 无 | 无（按设计） |
| ctf-crypto | 11 | 5 件齐全 | 无 | 无 |

**顺带暴露的一个坑（留待 P0-6）**：`data/session-mode.json` 是**进程级单文件**
且**优先于 `--default-mode`**——复测时三个模式返回同一份工具面，就是被一条
残留的 `session-mode.json` 覆盖了。三个 preset 并存时必须按 preset 分文件，
否则"选了 ctf-web 却按 pentest-standard 跑"且**无任何提示**。

### R-33 DSH web UI 在桌面浏览器里 `ERR_INCOMPLETE_CHUNKED_ENCODING`（观察，2026-09-24）

**现象**：真机冒烟时，桌面浏览器（Electron）打开 `http://127.0.0.1:4080/?token=…`

**待跟进**：① 换端口/重启浏览器进程后重测；② 若仍复现，向 DSH 侧反馈

### R-34 CTF 评测只有二值口径：看不出"差多少"（**已修** 2026-09-24，P2-2）

**问题**：33 题规模上 `8/33` 的信息量太低——分不清"全流程都在、最后差一步"与
"根本没入门"，也就无法判断一次改动是让中间步骤变强了还是只碰运气。

**设计（借 Cybench 的三口径，本地化）**：

| 口径 | 含义 | 与现状的关系 |
|---|---|---|
| `unguided` | 二值：判定器通过（flag 正确） | 与原来完全一致 |
| `subtask` | 里程碑完成比例（如 `2/3`） | **新增**：回答"差多少" |
| `subtask_guided` | 只算**最后一条**里程碑（= flag 收口） | 新增；**与 unguided 同值**（脚本化通路由同一份决策序列跑，不像 Cybench 那样因分档预算不同而分离——这点在代码注释里写明，不假装是两个独立指标） |

**里程碑规格（由类别与真值派生，不手写 33 份）**：

| 类别 | 里程碑 |
|---|---|
| 编码（单层，8 题） | ① 读取题面 ② 产出正确 flag |
| 编码（多层，20 题） | ① 读取题面 ② **剥掉最外层**（外层逆解码的中间态出现在工具输出里）③ flag |

### R-13 DSH preset 启动即带 `--authorize`，内层 ask 档失效（**已评审收口** 2026-09-23）

- **位置**：`dsh/.agent-presets/proteus/agent.cordis.yml` 的 `mcp-proteus` 行
  `args: ['-m','penagent','mcp','--data','data','--targets','127.0.0.1,localhost','--authorize']`
- **效果**：`--authorize` 是操作员级、服务端启动时一次设定 → 内核 `ask` 档在 DSH 会话内**不再拦截内层工具**，实际把关只剩 DSH 的 `approval` 档位
- **叠加风险**：`failOnStartupError: false` → 内核起不来时**静默丢掉全部工具**，不报错
  > **2026-09-22 补记**：这条已加机制性防线——`proteus-tools-policy.mjs` 的
  > **内核缺位守卫**在"工具面里没有 `mcp__proteus__*`"时对目标动作 fail-closed
  > （缺省 `kernelGuard: deny`，理由带排查命令），并把 `kernel` 标记写进证据链，
  > 链上因此能区分"被闸门拦下"与"内核根本没起来"。`--authorize` 那条仍是未决的
  > 设计选择（本节其余内容不变）。
- **建议**：文档明确写出"DSH 路径下靠的是哪一道闸"；评估是否需要 preset 侧不带 `--authorize`

**决策（2026-09-23）：保留 `--authorize`，并把这件事变成机检的不变量。**

依据是源码语义（`penagent/agent.py` 的 `Policy.check`）：MCP 是**非交互**通道，
内核的 `ask` 档**没有可问的人**——不带 `--authorize` 时：

```python
if level == "ask" and not self.authorize:
    return False, "…待人工确认（未执行）"        # 是拒绝，不是弹窗
if getattr(spec, "dangerous", False) and not self.authorize:
    return False, "高危工具 … 未授权（--authorize 才可执行）"
```

即：**去掉 `--authorize` 会让 sqlmap / nuclei / ffuf 这类工具全部不可用**，模型只能
转回宿主 shell——正是 R-1 与 R-11 那个"为了能用而放弃保护"的恶性循环。所以不能去掉。

代价要写清楚：DSH 会话里内核的 ask 档**不再是人的闸门**。`--authorize` 抬起的是
**内核的 ask 档与 dangerous 标记**，它**抬不动**这些（都不看 authorize）：

| 仍在内核侧生效 | 说明 |
|---|---|
| `capability.deny` / `permission.hard_deny` | 模式禁用与硬拒绝，任何开关都不放行（`test_hard_deny_not_releasable_by_authorize`） |
| `capability.constraints` | 参数冻结照旧追加 |
| `scope.target_allowlist` | 目标白名单（硬规则 3） |
| `scope.network_egress` | 出网闸门（两层：Policy + 沙箱） |
| 协议白名单（http/https） | `PolicyGate` 的 scheme 检查 |

于是 DSH 会话里的**人**那道闸是：**DSH 的 `approval` 档位**（host 平面）+
**目标动作裁决**（preset 平面，`ask`/deny，见 R-22 同批实现）。

**已加机检（`tools/dsh_install.py` 的 `verify_gate_consistency`）**：抬起了内核
ask 档 ⇒ host 补丁里**至少要有一个 `approval: ask` 的档位**；三档全 `never`
（无人值守最宽姿态）会被 `--check` 直接报出来。4 条回归用例 + 一条"仓库当前状态
必须过检"的回归锁。文档侧见 `docs/DSH宿主接入指南.md` 第八节第 12 条。

### R-40 LLM 输出非法 JSON 直接判任务失败，无重试（**已修** 2026-09-24）

- **原证据**：真机渗透任务第 13 步收到 `<｜｜DSML｜｜ invoke name="http_raw">` 形态的 XML 工具调用，

  保持原来的 fail-fast 语义）
- **重试方式**：`PenAgent._decide` 回灌纠正提示（`_parse_correction`：说清"上一条输出无法解析

  **预算耗尽后的强制收口**两处调用都走这条路径
- **刻意取舍**：① **重试不记步数**——解析失败没产生任何决策或工具调用，按步数记账等于替一次
  格式失误扣掉一步真实预算（`max_steps=1` 的用例钉住这一点）；② 阈值不进 ModeProfile
  （同 R-39：模型行为纠偏而非模式语义，各模式判据相同）；③ `LLMOutputError` 继承 `LLMError`，
  既有消费方（如 `reflect.py` 的降级分支）行为不变
- **留痕**：每次不可解析都写一条证据（`phase=llm_parse_retry`，含 `attempt` / `error` / 原始输出
  片段 `raw`），事后可判"模型形态失误"还是"端点异常"；收口理由写明"输出连续 N 次不可解析"
- **锁定**（`test_agent.py` 五条 + `test_llm_client.py` 两条）：
  `test_llm_parse_failure_is_retried_instead_of_failing`（救回 + 纠正提示回灌 + 留证）、

  `test_llm_transport_error_still_fails_fast`（调用失败一次即收口）、
  `test_llm_parse_retry_does_not_consume_step_budget`（`max_steps=1` 时那一步仍能执行工具）、
  `test_llm_parse_retry_covers_forced_conclusion`（收口调用同样可重试）、

- **边界**：只兜"输出形态"；模型持续给出合法 JSON 但内容无用，仍按原判定逻辑收口

### R-46 首次推送 52 个提交把 CI 全推红：三类平台/依赖缺陷被"本地全绿"掩盖（**已修** 2026-10-01，`79ec5d4`、`8b98b7c`）

**现象**：批量提交首次推送后 CI 三个 job 全挂在 `Run tests`（Windows 3.12/3.13 各
6 failed、Linux 14 failed），而本机全量 `657 passed / 0 failed`。这批提交在本地压了
数天从未推送，CI 没机会看——**"本地绿"被当成了"可以推"**。

**真值**（三类，逐条实证；都不是误报）：

1. **硬编码 `python.exe`**（Linux 8 条）：`PENTEST_PY312` 的语义是**目录**，四处写死
   `${py}/python.exe`，Linux 上拼出 `/opt/hostedtoolcache/.../bin/python.exe` → ENOENT
   ——`/proteus-evidence`、`/proteus-skills`、`/proteus-tree`、`/proteus-scope` 四个
   命令在 Linux 上全线失效。同类**第二处更重**：cordis 模板 `mcp-proteus` 的 `command`
   也写死 `python.exe`，Linux 上内核 MCP 根本起不来。
2. **校验基准取错**（Windows 6 条）：`checksec_bin` / `nuclei_scan` 依赖**可选依赖**
   （pwntools 的 `pwn`、RsaCtfTool、PENTEST_TOOLS 工具库），CI 没装即"不可用不注册"。
   但 `test_mode_tool_lists_reference_real_names` 拿"**已注册名**"当基准，把
   `modes/*.yaml` 里**合法**的 `checksec_bin` 声明误报成"不是真实注册名"——"拼写错误"
   与"缺依赖"被混成同一个信号。
3. **换绑没关监听套接字**（Linux 2 条，第 1 类修完后才暴露）：`penagent/oob.py::_start_locked`
   换绑只调 `srv.shutdown()`——它**只停 `serve_forever` 循环，不释放监听套接字**。POSIX 上
   紧接着绑同端口必 EADDRINUSE，"端口上移"容错于是把同端口换绑**悄悄换成换端口**，旧端口
   留个半死监听（连接能进、没人接）。Windows 的 SO_REUSEADDR 允许覆盖，把这条完全盖住。

**修法**：

- 新增 `kernelPython()`（按平台取文件名 + 探测存在的候选；`PENTEST_PY312` 直接指向解释器
  本身也照用），四处调用换用，Windows 行为与改动前逐字节一致。cordis 模板改为
  `(process.platform==='win32'?'python.exe':'python3')`——注意该行是 `!!js`，表达式里禁止
  出现冒号加空格（YAML 会拆映射键），所以三元**不带空格**（与文件里既有的
  `customSkillDirs` 同口径）。
- `ToolCenter` 新增 `_declared` + `declared_tool_names()`（已登记 ∪ 声明过的，含未注册的）；
  `load_external_tools` 结构化返回 `unavailable`。**校验配置用声明全集，校验运行期工具面
  仍用 `all_entries()` / `discover()`**——拼写错误照样抓，缺依赖不再误报。依赖外部工具链的
  用例照 `test_m3.py` 既有口径补显式 skip（理由写明缺什么、怎么装），不静默通过；其中
  "渗透面看不见 `checksec_bin`"这半边与依赖无关，仍无条件钉住。
- `_start_locked` 换绑补 `srv.server_close()`。

**重测（2026-10-01）**：

- 正常环境全量 **658 passed / 19 skipped / 0 failed**；**伪造 CI 环境**（PATH 去掉
  Python 3.12.9 脚本目录 + `PENTEST_TOOLS=` 置空）**655 passed / 22 skipped / 0 failed**

- 平台解析真跑复核：在真实 mjs 上伪装 `process.platform=linux` 得 `<dir>/python3`、
  `win32` 得 `<dir>/python.exe`。
- 新增 `test_rebind_releases_old_listener_socket`：判据刻意落在**"旧套接字已释放"**
  （`stale.socket.fileno() == -1`）而不是"端口号没变"——后者在 Windows 上恒真、抓不到回归。
  撤掉 `server_close()` 该用例即转红（`assert 628 == -1`）。
- `render_preset_bundle.py` 重渲染 + `dsh_install.py --check` 通过（bundle 与 `_shared`
  一致、三声明齐全）；`test_preset_bundle` / `test_dsh_install` **57 passed**。
- CI 实跑：Windows 3.12 / 3.13 **success**，整体 run 结论 **success**
  （`test-linux` 因 `continue-on-error` 不阻塞）。

**遗留**：① `AGENTS.md` 的测试基线（564）已显著滞后于实际（657），且未记录"CI 环境 vs
本机环境"的 skip 差异——待专门一轮对齐；② `test-linux` 是"实验性信号"，本次修完不再有断言
