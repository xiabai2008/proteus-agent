# 能力加强路线（DSH 主线）

> 建档：2026-09-21　　前提：**以 DSH 宿主为日常主调用方式**（CLI/MCP 保留为无宿主场景的兜底）。
> 依据：本轮代码实测 + 公开资料查证。**未核实的内容明确标注**，不混入已验证结论。
> 配套文档：`docs/修复待办清单.md`（可修复点，编号 R-*）。

---

## 零、先说一个架构事实：DSH 会话里有两个 agent

这是所有后续讨论的基准，先摆清楚：

```
DSH 会话
  └─ DSH 会话 Agent（驱动对话的模型）
       拥有：文件读写 / shell / 搜索 / jobs / skills / goal / plan mode /
             compaction（上下文压缩）/ tool-result-pruner / subagent(spawn+fork) /
             workflow / ralph / todo / web 搜索 / ask-user
       │
       └─ 调 mcp__proteus__pentest_run → Proteus 内核 Agent
             拥有：自己的 ReAct 循环 / 证据链 / 模式裁决 / 24 个安全工具
             没有：上下文压缩 / 计划模式 / 子代理 / 并行 / 联网搜索
```

**当前设计把决策权交给了内层**（`prompts/dsh-persona.md` 把内核描述为执行者，但 `pentest_run` 实际让内核自己跑完整 ReAct 循环）。于是出现了能力倒挂：

| 能力 | DSH 会话 Agent | Proteus 内核 Agent |
|---|---|---|
| 上下文压缩 | 有（`compaction-basic` + `tool-result-pruner`，threshold 8192 字符） | **无** |
| 计划/分解 | 有（plan mode） | 无 |
| 并行执行 | 有（subagent spawn/fork + workflow） | 无（单线程串行） |
| 联网检索 | 有（`dsh-tool-web`） | 无 |
| 安全工具 | 无 | 有（24 个） |
| 证据链/反幻觉 | 无 | 有 |
| 模式裁决 | 无（DSH 侧只有沙箱/审批） | 有 |

**结论**：把"长任务编排"交给外层的 DSH agent、把"工具执行 + 证据固化 + 模式裁决"交给内层内核，是更省力的分工。当前 preset 的工具清单里**两条路并存**（`pentest_run` 和 24 个裸工具），但没有指导模型该走哪条——这是需要设计的地方，不是靠提示词自觉。

## 一、公开资料查证结果

### 1.1 DSH（deepseek-harness）生态 — 已验证

`github.com/deepseek-ai/deepseek-harness`：**231k stars / 27.7k forks / 18,059 commits**（2026-09 抓取）。
含义：生态极大且迭代快——好处是插件面持续增强（白拿能力变多），风险是**上游 RC 版会 breaking**（README 已把这条列为排除"魔改 DSH 当内核"的理由之一，判断正确）。

### 1.2 XBOW — 已验证（标杆，且其方法论与本项目同源）

- 真实商业公司，2025 年其 Agent 曾在 **HackerOne 美国榜登顶**（多个来源交叉确认）
- **核心能力差异**（引用其自我表述）：*"不是扫到漏洞就报，而是真正尝试利用它"* —— 即 **验证优先**
- 这与本项目 `prompts/pentest.md` 的"可复现 PoC 是结论的最低门槛"、`verifier.py` 的 `require_poc` **是同一个信念**。方向没错，缺的是工具支撑。

### 1.3 XBOW validation-benchmarks — 已验证，但有一个关键警告

`github.com/xbow-engineering/validation-benchmarks`（708 stars / 217 forks / 44 commits）：
- 104 个基准，Web 攻击为主，Jeopardy 式 CTF
- `make build FLAG=xxx` 注入 flag，基于 docker-compose，**结构可直接借鉴**
- **关键**：其 README 明确声明——2026 年中期该基准**已被行业饱和（~100% 性能）**，不再具备区分度

**含义**：不要把它当作"目标分数"来源；但它的**组织形式**（docker 靶场 + 可注入 flag + 自动判定）是自建评测的现成模板。评测的真正价值在**自建、贴自己场景**的题集。

### 1.4 参考实现 — 已验证存在

`github.com/m-sec-org/xbow-competition`：一个"AI Agent 自动化 XBOW 解题方案，结合 MCP 服务器和智能 CLI 客户端"。**与本项目架构同构**，值得对比阅读其工具设计与编排方式。

### 1.5 未能核实的部分（如实声明）

- arxiv 的 AutoPenBench 等学术基准页面**抓取超时**，未取得原文
- 中文检索被搜索引擎污染，多数结果无效（已弃用）

## 二、六个加强方向

### 方向 A · 宿主层：明确"哪一层做决策"（**最高杠杆，先做这个**）

**做什么**：
1. 在 `prompts/dsh-persona.md` 里明确分工原则——**长任务编排（分解、并行、进度跟踪）由外层做；具体工具调用与证据固化走内核**。
2. 给 `pentest_run` 与裸工具之间定规则：什么时候该用哪个（例如：单点侦察用裸工具省一层 LLM 往返；完整任务链用 `pentest_run`）。
3. 评估是否把 `pentest_run` 从工具清单里**降权或改名**（如 `pentest_full_task`），让它不再是默认选项。

**为什么**：这是零成本（改提示词）但影响最大的——直接决定模型能不能用上 DSH 的 compaction/并行/计划能力。

**验收**：DSH 会话里下一个复合任务（如"扫三个目标并出对比报告"），观察模型是否用 subagent 并行而非串行三次 `pentest_run`。

---

### 方向 B · 工具层：从"扫描器"到"验证者"（**能力的核心缺口**）

**现状**（本轮实测）：24 个内置+CLI 工具**全部是侦察/扫描类**，零利用、零验证、零后渗透。

**XBOW 的启示**：差异不在"扫得更全"，在"能验证打得穿"。

**做什么**（按风险递增）：
1. **PoC 验证工具**（安全）：把已有的 `sqlmap` / `nuclei` 从"扫描模式"扩到"验证模式"（`--verify` 类参数），产出可复现 PoC 而非"疑似存在"
2. **HTTP 重放工具**（安全）：一个能原样重放证据里那条请求的工具——让"可复现 PoC"从文档要求变成可执行动作
3. **利用类工具**（需 `require_confirm` + 容器隔离）：PoC 框架（`pocsuite` 已在列，但只有一个 `--batch` 入口）
4. **报告生成器**：从证据链直接产出标准渗透报告（Markdown/HTML）——**报告才是交付物**

**注意**：本机 Docker 当前不可用（R-11），新增需隔离的工具会直接撞上这个限制。**先解决 R-11 的可用性，否则新增隔离工具等于新增一堆拒绝**。

---

### 方向 C · 知识层：把已接入但没接上的能力连起来

**现状**：
- `seckb` 本地网安知识库（1175+ 篇）已声明在 `mcp_servers.json`，但**主路径从不连接**（R-14）
- 技能库无种子，全靠 `reflect.py` 从成功任务涌现（冷启动）
- `ModeProfile.skills` 字段无消费方（R-3）

**做什么**：
1. 修 R-14：加 `--discover-mcp` 开关，让 seckb 真正可用——**这是现成的知识来源，接上就有 1175 篇可检索**
2. 建**种子技能库**：把渗透 SOP（SQLi/SSRF/上传/越权的验证步骤）写成初始技能，不再纯靠涌现
3. 修 R-3：让 `mode.skills` 真正参与检索过滤

**为什么**：知识复利是项目唯一的复利来源，但当前是零起点。seckb 是最快的一步。

---

### 方向 D · 评测层：**最大的空白**（本轮最重要的判断）

**现状**：
- 224 个测试**全测机制**（模式、闸门、沙箱、判定器），**零测能力**
- 能回答"模式切换正确吗"，**不能回答"这个 agent 强不强"**
- CTF 评测只有 3 道玩具题（`data/eval-ctf/`）

**含义**：没有能力度量，**任何能力投入都无法判断是否变好**。这是所有后续方向的前置条件。

**做什么**：
1. **自建 CTF 题集**（50–100 题，公开源/自建，自动校验 flag）——扩展现有 `examples/eval_ctf_solve.py` 到规模化
2. **自建渗透靶场套件**（DVWA / Juice Shop / vulhub 等，带"预期发现清单"）
3. **评分卡**：一条命令跑完 → 输出解出率 / 步数 / 成本 / 误报率
4. 借鉴 XBOW validation-benchmarks 的**组织形式**（docker + flag 注入 + 自动判定），但**不追它的分数**（已饱和）

**验收**：`python examples/eval_benchmark.py` 一条命令输出评分卡，且分数可跨版本对比。

---

### 方向 E · 上下文层：长任务的能力天花板

**现状**：`agent.py` 的 ReAct 循环把**全部历史步骤**累积进 `messages`，无压缩、无剪枝。步数一多必然爆上下文——这是内核侧的硬天花板。

**做什么**：
1. 给内核循环加**历史摘要压缩**（参照 DSH 的 `tool-result-pruner` 思路：threshold + head/tail 保留）
2. 工具输出的截断策略当前是硬编码（`str(output)[:1500]`），改为**按信息量自适应**

**为什么**：渗透任务动辄几十步，不压缩就走不远。这也是"内层 agent 不如外层"的根因之一——外层有 compaction，内层没有。

---

### 方向 F · 安全可用性：让保护不成为负担

**现状**（本轮实测，见 R-1 / R-11）：
- 不传 mode → 危险工具**直跑宿主**（无隔离）
- 传 pentest-standard → 危险工具**全被拒绝**（Docker 挂了）
- 结果：为"能用"而放弃 mode，等于放弃全部模式保护

**做什么**：
1. **修 R-1**（最高优先）：给 MCP server 加默认模式，mode 从"模型可选参数"提升为"服务端配置"
2. **修 R-11 的可用性表达**：容器不可用时给出**可操作的提示**，或提供"降级为 local 但需显式确认"的档位
3. **对齐 R-6**：`proteus-ctf` 的 approval 值三处统一
4. **修 R-13 的表达**：明确写出 DSH 路径下"实际把关的是哪一道闸"

**为什么**：安全机制如果不能顺畅工作，就会被绕过——R-1 与 R-11 正在形成这个恶性循环。

## 三、优先级建议

| 优先级 | 方向 | 理由 |
|---|---|---|
| **P0** | F 修 R-1 | 违反硬规则 1；且是"保护反成负担"的源头 |
| **P0** | D 评测层 | 无度量则后续所有投入无法验证 |
| **P1** | C 知识层修 R-14 | 成本最低、收益立即（接上就有 1175 篇） |
| **P1** | A 宿主层分工 | 零成本（改提示词），影响大 |
| **P2** | B 工具层 | 价值高但受 R-11（Docker）阻塞，需先解可用性 |
| **P2** | E 上下文层 | 天花板问题，但步数少时不痛 |

**串行建议**：R-1 → R-11 可用性 → D 评测骨架 → C 接 seckb → A 分工 → B 工具 → E 压缩。

## 四、反目标（明确不做）

1. **不要在建立度量前加新模式**——无法判断是否变好
2. **不要在单 agent 可靠前上 multi-agent**——复杂度是乘法
3. **不要追 XBOW 基准分数**——该基准 2026 已饱和，无区分度
4. **不要为"降级能跑"而削弱 fail-closed**——项目最硬的部分是"容器不可用时拒绝而非裸跑"，宁可不可用也不裸跑；正确做法是修基础设施与提示，不是拆闸门
5. **不要魔改 DSH 核心**——上游 RC 版会 breaking（README 的判断是对的）
