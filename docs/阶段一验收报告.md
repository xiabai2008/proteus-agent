## 二、逐条自检

### 验收项 1：同一内核同一目标两种模式输出不同判定 —— 通过

演示脚本 `examples/eval_mode_switch.py`（全离线：LLM 用脚本化决策替代，工具是纯函数桩，不发起任何真实网络请求；目标 `http://127.0.0.1:8080`）：

```
====================================================================
[1] pentest-standard：verifier=evidence_chain
====================================================================
  模式: pentest-standard | 判定器: EvidenceChainVerifier | require_poc=True
  步数预算(来自模式 budget.max_steps): 40 | 记忆分区: pentest-standard
  工具 schema: ['http_test', 'nuclei']
  -> 判定: success | 步数 2
  -> 结论: 目标 200 可达，标题 Demo Portal
  -> 证据引用: [1]

====================================================================
[2] ctf-web：verifier=flag_regex（同一内核、同一目标）
====================================================================
  模式: ctf-web | 判定器: FlagRegexVerifier | pattern='(?i)(flag|ctf)\{[^}]+\}' auto_retry=3
  步数预算(来自模式 budget.max_steps): 60 | 记忆分区: ctf-web
  工具 schema: ['http_test']
  -> 判定: success | 步数 2
  -> 结论: flag{mode-switch}

  [2b] 同样收口但结论里没有 flag：CTF 判定器不给过
  -> 判定: failed | 步数 4
  -> 原因: 未命中 flag 正则 '(?i)(flag|ctf)\{[^}]+\}'（重试已耗尽）
```

**判定差异的三个可观测点**：

1. **判据不同**：同一句「目标 200 可达」在渗透模式通过（引用真实证据即可），在 CTF 模式不通过（必须命中 flag）；反过来，`flag{...}` 在渗透模式只是一段文本，不构成成功判据。
2. **重试语义不同**：CTF 的 `auto_retry: 3` 允许未命中时回灌原因再试（演示 [2b] 中 4 次判定后耗尽），渗透模式默认不重试。
3. **能力面不同**：同一份工具注册表，渗透模式放出 `['http_test', 'nuclei']`，CTF 模式只放出 `['http_test']`（`nuclei` 既不在 allow 内也在 deny 内）。

对应测试：`tests/test_verifier.py`（14 例）、`tests/test_modes.py`（18 例）、`tests/test_policy_mode.py`（12 例）。

### 验收项 2：禁用工具被机制性拒绝 —— 通过

同一次演示的 [3] 段：

```
  registry.get('nuclei') -> None
  工具 schema 含 nuclei -> False
  提示词含 nuclei -> False
  -> 拦截原因: 模式 ctf-web 禁用该工具：工具 nuclei 被当前模式 capability.deny 禁用
  -> 留证档位: ['deny']
```

**机制性而非提示词劝退的证据链**：CTF 模式构造内核时按 `capability` 过滤注册表，`nuclei` 根本不进注册表 → ①不进 system prompt 的工具 schema（模型看不见）；②`registry.get()` 返回 `None`，执行层不可达；③即便模型凭空点名调用，主循环也走模式拒绝分支，并在证据链留下 `blocked: true, level: deny` 的记录。三个条件同时成立才说明"拦截发生在执行前"。

对应测试：`test_ctf_mode_denied_tool_unreachable`（拦截 + 未执行 + 留证）、`test_capability_deny_blocks_before_execution`（allow 为 `*` 时 deny 仍生效）、`test_hard_deny_not_releasable_by_authorize`（hard_deny 连运行期授权也不放行）。

### 验收项 3：步数超限换策略而非崩溃 —— 通过

演示 [4] 段，用 pentest-standard 的 `budget.max_steps: 40`（非硬编码），脚本化决策连续 40 轮调工具、第 41 轮收口：

```
  模式预算: max_steps=40（pentest-standard.yaml）
  脚本化决策: 连续 40 轮调工具，第 41 轮为收口
  -> 判定: success | 记录步数 40
  -> 结论: 已在预算内完成侦察
  -> 留证阶段标记: ['budget_exhausted', 'budget_concluded']
```

实现语义：步数用尽后**不硬退出**，改为追加一轮「强制收口」——要求模型停止调用工具、基于已有证据给出结论，再交同一个判定器裁决。收口轮仍受判定器约束（CTF 仍要 flag，伪造证据仍被反幻觉拦截），因此"换策略"不等于放宽判据。

对应测试：`test_budget_max_steps_from_mode`（模式预算生效、显式传参优先）、`test_budget_exhausted_switches_to_conclude`（换策略后成功收口）、`test_budget_exhausted_conclude_still_verified`（收口轮仍要过判定，失败也不抛异常）、`test_budget_exhausted_in_ctf_mode_still_needs_flag`。

## 四、本轮新增：记忆分区

`Memory(root, namespace=...)` 把作战记录与经验库落到 `missions/<namespace>/` 与 `skills/<namespace>/`；内核在构造时按 `mode.memory_namespace` 绑定分区，`_rank_skills` 与技能回写因此天然只在本分区检索，模式间互不串库。分区名经 `_safe_namespace` 校验（拒绝 `..`、路径分隔符等，防止越出数据目录）。

验收演示中的体现：pentest-standard 的记忆分区为 `pentest-standard`，ctf-web 为 `ctf-web`（见演示输出）。对应测试 `test_skills_isolated_between_namespaces`（同名技能 `web-chain` 在两个分区各自独立、互不可见）、`test_missions_isolated_between_namespaces`、`test_rank_skills_scoped_to_mode_namespace`（渗透分区的技能不会被 CTF 任务注入）。

## 五、未达标项与阻塞说明

**未达标的是「全量 pytest 绿」，5 个失败用例：**

| 失败用例 | 原因 |
|---|---|
| `test_rl.py::test_train_script_runs` | 依赖的 `examples/train_policy.py` 缺失 |
| `test_ppo.py::test_train_ppo_script` | 同上（间接 import） |
| `test_closed_loop.py::test_closed_loop_script` | 同上 |
| `test_closed_loop.py::test_evaluate_uses_independent_hosts` | 同上 |
| `test_m3.py::test_evolution_llm_script_mock` | 依赖的 `examples/eval_evolution_llm.py` 缺失 |

这两个脚本**不是本次改动引入的缺失**，而是 fork 时被本机 Mimosa 安全门禁以「SQL 注入」为由拦截写入（误报：命中行是内核自身的工具调度 `reg.execute(tool, {...})`，文件中没有任何 SQL）。放行后即可补齐并使 5 个用例转绿，阶段一即为全绿收口。

**同类阻塞：三次 commit 均被 Mimosa L3 项目级扫描拦截**，报 3 条高危 SSRF（`builtin_tools.py:36/73` 的 `http_probe`/`robots_fetch`、`llm.py:86` 的 LLM 客户端——均为"工具职责就是发 HTTP 请求"）与 8 条低危弱随机数（`random.Random(seed)`，训练与测试可复现所需）。这些均为误报；为迎合扫描器改写它们会阉割功能或破坏可复现性，故未改。解除方式：在 Mimosa 中放行上述两类规则。

## 六、遗留项（不属阶段一验收范围，建议后续处理）

1. **MCP 入口未收口**：`penagent/mcp.py:126` 的底层工具分支直连 `registry.execute`，既不过 Policy 也不带模式与判定器。内核主循环已具备「能力过滤 → 策略裁决 → 判定收口」三道闸，MCP 入口仍是裸的。
2. **预算字段未全接线**：`budget.max_minutes` / `max_cost_usd` 尚未生效（`max_steps` 已生效）；`model_tier` 分级路由未实现。
3. **CTF 模式工具面偏窄**：`ctf-web` 的 `capability.allow` 只列了 5 个抽象工具名，与内置工具（`port_scan`/`http_probe`/`dns_lookup`/`robots_fetch`）无交集，实际运行时 CTF 模式的可用工具为空——阶段二接入 CTF 工具时应同步对齐命名。
4. **`permission.default: ask` 的实际影响**：两个基准模式都继承 base 的 `ask`，未加 `--authorize` 时工具调用会被记为「待人工确认」。这是配置语义（fail-safe），如需无人值守运行应在模式 YAML 中调整 `auto_approve` 或 `default`。
